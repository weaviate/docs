# API specification files

Machine-readable API specifications published by this docs site. Everything under
`static/` is copied verbatim into the build, so a file here at
`static/specs/<name>.json` is served at `https://docs.weaviate.io/specs/<name>.json`.

## `weaviate-openapi.json`

### What it is

Weaviate's REST API specification, in **Swagger 2.0** (OpenAPI 2.0) format. It is
not OpenAPI 3.x, so a consumer that only accepts 3.x has to convert it first. Its
`info.version` field says which Weaviate version this copy describes.

It is built from `openapi-specs/schema.json` at a Weaviate release tag in
[weaviate/weaviate](https://github.com/weaviate/weaviate). In Weaviate that file
is the input to the code generator that produces the REST server and its models.
It defines the API rather than describing it after the fact.
`weaviate-openapi.source.json` records the provenance: the tag, the commit it
points at, when it was fetched, and a hash of the overlay that was applied.

### How it is built

**Do not edit this file by hand.** The next build overwrites it, and a test fails
while it differs from the build output. Everything that produces it lives in
[`_build_scripts/openapi/`](../../_build_scripts/openapi/):

| File | What it is |
| :-- | :-- |
| `upstream/schema.json` | The upstream spec at the pinned tag, byte for byte. Each refresh replaces it, so the PR shows the upstream diff. |
| `overlay.json` | The docs-specific changes, as an [RFC 7386](https://www.rfc-editor.org/rfc/rfc7386) JSON Merge Patch. |
| `overlay.lock.json` | A hash of the upstream value under every overlay entry. |
| `build_spec.py` | The build. Python standard library only. |

The build runs in three stages: upstream, then the rule, then the overlay.

**The rule.** Every `<br/>` in a `description` or `summary` becomes a newline.
Upstream writes `<br/>`, and the Scalar reference renders Markdown. The rule is
mechanical, so the overlay does not carry text that differs from upstream only in
line breaks.

**The overlay.** A merge patch sets a value, deletes one with `null`, or merges
into an object. Arrays are replaced whole. Today it carries the `servers` block
the Scalar request builder uses, the removed `basePath`, the narrowed `consumes`,
the rewritten top-level `tags`, and the per-operation `tags` of the root,
well-known and batch endpoints. Keep it small. When a release says the same as an
override, remove the override.

**The lock and the drift report.** An override hides whatever upstream has at
that location. So for each overlay entry the lock stores a hash of the upstream
value it replaced, or `absent`. `--check-lock` compares a new upstream against
the lock and classifies every entry:

| Status | Meaning | Effect |
| :-- | :-- | :-- |
| ok | Upstream has not changed under the override. | None |
| drifted | Upstream changed the value the override replaces. | Reported. Review the override. |
| stale | The target no longer exists upstream. | The build fails. Remove the entry. |
| unlocked | The entry has no lock record. | Reported. Run `--update-lock`. |

### The nightly job

[`.github/workflows/openapi_spec_nightly.yml`](../../.github/workflows/openapi_spec_nightly.yml)
runs at 03:00 UTC. It picks the highest `vX.Y.Z` release that is neither a draft
nor a prerelease. It does not use GitHub's "latest release" marker. That marker
follows publication date, so a 1.38 patch published after a 1.39 patch would win.
When the tag matches the one in `weaviate-openapi.source.json`, the job stops
after that one API call. When an open refresh PR for that tag, built with the
current overlay, already waits for review, it stops after three calls, so it does
not rebuild and force-push the PR every night. A bot PR closed without merging is
rebuilt automatically the next night.

Otherwise it downloads the spec for that tag and checks that it is a Swagger 2.0
document for exactly that version, with paths. Then it rebuilds the spec, writes
the drift report to the run summary, and runs the spec tests and
`yarn build-dev`. If anything changed, it opens or updates a PR from branch
`chore/refresh-openapi-spec`. The PR body carries the tag, path and definition
deltas, with a link to the drift report. A human still reviews and merges, so the
published API contract never changes unattended.

Fix drift or overlay problems with a PR to `main`. Never commit them on the bot
branch, because the next release force-pushes it.

A dispatch on `main` accepts only release tags (`vX.Y.Z`). Prereleases never
publish to `main`.

To run it now, or to build from a specific tag such as a release candidate for a
version branch, dispatch it from the Actions tab or the command line:

```bash
gh workflow run openapi_spec_nightly.yml
gh workflow run openapi_spec_nightly.yml -f tag=v1.40.0-rc.1 -f base=<docs-version-branch>
```

A dispatch against a base other than `main` uses its own PR branch,
`chore/refresh-openapi-spec-<base>`, so it never replaces the PR against `main`.

**If the job appears to do nothing**, its header comment records the two usual
causes. The repository or organization needs "Allow GitHub Actions to create and
approve pull requests" enabled, or the final step fails with a 403 from
`gh pr create`. And a push made with `GITHUB_TOKEN` does not start other
workflows. The job runs the spec tests and the dev build itself for that reason.
The link checks still do not run on its PR. Close and reopen the PR to run them
before merging.

### Adding a docs-specific edit

1. Edit `_build_scripts/openapi/overlay.json`. Address the value by its path in
   the spec. Replace an array whole.
2. Record what upstream has under the new entry:

   ```bash
   python3 _build_scripts/openapi/build_spec.py \
     --upstream _build_scripts/openapi/upstream/schema.json \
     --overlay _build_scripts/openapi/overlay.json \
     --lock _build_scripts/openapi/overlay.lock.json \
     --tag "$(jq -r .tag static/specs/weaviate-openapi.source.json)" \
     --update-lock
   ```

3. Rebuild the spec with the last command in the next section. Use the tag and
   commit already in `weaviate-openapi.source.json`.
4. Run the tests:

   ```bash
   uv run pytest -m openapi -q tests/openapi
   ```

### Building by hand for a tag

This is the sequence the job follows. Use it for an urgent refresh or to debug
the job.

```bash
TAG=v1.39.7

# The commit the tag points at. An annotated tag points at a tag object first.
OBJ=$(gh api "repos/weaviate/weaviate/git/ref/tags/$TAG" --jq .object)
if [ "$(jq -r .type <<< "$OBJ")" = tag ]; then
  OBJ=$(gh api "repos/weaviate/weaviate/git/tags/$(jq -r .sha <<< "$OBJ")" --jq .object)
fi
COMMIT=$(jq -r .sha <<< "$OBJ")

gh api "repos/weaviate/weaviate/contents/openapi-specs/schema.json?ref=$TAG" \
  -H "Accept: application/vnd.github.raw" > /tmp/weaviate-schema.json
jq '{swagger, version: .info.version, paths: (.paths | length)}' /tmp/weaviate-schema.json
cp /tmp/weaviate-schema.json _build_scripts/openapi/upstream/schema.json

python3 _build_scripts/openapi/build_spec.py \
  --upstream _build_scripts/openapi/upstream/schema.json \
  --overlay _build_scripts/openapi/overlay.json \
  --lock _build_scripts/openapi/overlay.lock.json \
  --out static/specs/weaviate-openapi.json \
  --source-out static/specs/weaviate-openapi.source.json \
  --tag "$TAG" --upstream-commit "$COMMIT" \
  --check-lock --report /tmp/drift.md
```

Check the printed version against the tag, and read the drift report. Once you
have reviewed the drifted entries, rerun with `--update-lock` to record the new
upstream values.

**Why the temp file matters.** `>` truncates the target before `gh` runs, and
`gh api` writes its error body to stdout. Redirecting straight onto a tracked file
overwrites a good spec with a 141-byte GitHub 404 object. `gh` does exit non-zero,
but the file is already gone by then. Fetching to a temp file keeps the committed
copy intact until you have seen what arrived.

**The `v1-39/openapi-for-docs` branch is retired.** The docs spec used to be a
copy of a hand-merged branch in weaviate/weaviate. Its docs-specific changes now
live in `overlay.json`. Do not edit that branch, and do not add new
`v*/openapi-for-docs` branches.

### Why it is served the way it is

**One file, two consumers.** This committed copy is the single source of truth
for the REST API on this site: `netlify.toml` serves it at `/openapi.json`, and
the human-readable reference at `/weaviate/api/rest` is rendered from the same
file (the Scalar plugin in `docusaurus.config.js` reads this path). The published
spec and the rendered reference therefore cannot describe different versions of
the API, and there is no branch pin to keep in sync.

**`/openapi.json` only — there is deliberately no `/swagger.json` alias.** Swagger
2.0 *is* OpenAPI 2.0, so `/openapi.json` names today's document accurately, and it
is the path tooling probes by convention. It also stays accurate if the spec is
ever converted to OpenAPI 3.x, whereas a 3.x document served at `/swagger.json` is
exactly what a Swagger-era client cannot consume.

**A committed copy, not a proxy to GitHub.** Proxying `/openapi.json` to
`raw.githubusercontent.com` does return the file, but the response carries the
origin's `content-type: text/plain` and `x-content-type-options: nosniff`, and
Netlify `[[headers]]` rules do not apply to proxied responses, so the content type
cannot be corrected. Netlify sets the content type itself for files it hosts, so
this copy is served as `application/json`.

### Testing the route locally

The rewrite is a Netlify feature and does not exist for the plain static server
used by `yarn validate-links-dev`, so `/openapi.json` 404s in that lane and is
skipped there. Check it with `netlify dev` instead:

```bash
yarn build && npx netlify dev --offline --dir build
curl -sI http://localhost:8888/openapi.json   # 200, content-type: application/json
```
