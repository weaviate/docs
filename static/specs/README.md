# API specification files

Machine-readable API specifications published by this docs site. Everything under
`static/` is copied verbatim into the build, so a file here at
`static/specs/<name>.json` is served at `https://docs.weaviate.io/specs/<name>.json`.

## `weaviate-openapi.json`

### What it is

Weaviate's REST API specification, in **Swagger 2.0** (OpenAPI 2.0) format — not
OpenAPI 3.x, so a consumer that only accepts 3.x has to convert it first. Its
`info.version` field says which Weaviate version this copy describes.

It is a copy of `openapi-specs/schema.json` from the newest `v*/openapi-for-docs`
branch of [weaviate/weaviate](https://github.com/weaviate/weaviate). In Weaviate
that file is the input to the code generator that produces the REST server and
its models, so it defines the API rather than describing it after the fact.

### Refreshing it

**Do not edit this file by hand** — an edited copy would describe an API that
Weaviate does not implement. Replace it whole, from the newest
`v*/openapi-for-docs` branch:

```bash
# BRANCH is the whole branch name, slash included: v1-39/openapi-for-docs
gh api "repos/weaviate/weaviate/contents/openapi-specs/schema.json?ref=${BRANCH}" \
  -H "Accept: application/vnd.github.raw" > static/specs/weaviate-openapi.json
```

Refreshing is manual, so this copy can lag the newest Weaviate release.

### Why it is served the way it is

**One file, two consumers.** This committed copy is the single source of truth
for the REST API on this site: `netlify.toml` serves it at `/openapi.json`, and
the human-readable reference at `/weaviate/api/rest` is rendered from the same
file (the Scalar plugin in `docusaurus.config.js` reads this path). The published
spec and the rendered reference therefore cannot describe different versions of
the API, and there is no branch pin to keep in sync.

**`/openapi.json` only — there is deliberately no `/swagger.json` alias.** Swagger
2.0 *is* OpenAPI 2.0, so `/openapi.json` names today's document accurately, and it
is the path tooling probes by convention. It also stays accurate if the spec is
ever converted to OpenAPI 3.x, whereas a 3.x document served at `/swagger.json` is
exactly what a Swagger-era client cannot consume.

**A committed copy, not a proxy to GitHub.** Proxying `/openapi.json` to
`raw.githubusercontent.com` does return the file, but the response carries the
origin's `content-type: text/plain` and `x-content-type-options: nosniff`, and
Netlify `[[headers]]` rules do not apply to proxied responses, so the content type
cannot be corrected. Netlify sets the content type itself for files it hosts, so
this copy is served as `application/json`.

### Testing the route locally

The rewrite is a Netlify feature and does not exist for the plain static server
used by `yarn validate-links-dev`, so `/openapi.json` 404s in that lane and is
skipped there. Check it with `netlify dev` instead:

```bash
yarn build && npx netlify dev --offline --dir build
curl -sI http://localhost:8888/openapi.json   # 200, content-type: application/json
```
